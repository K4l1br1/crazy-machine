# TEST_PLAN — «Торнадочайник-3000»

Обозначение ТЗ: ТЗ-ТЧ3000-03-2026.
План описывает, как проверять реализацию `tornado_teapot.py` тестами из `tests/`. Результаты, версия Python, ОС и коммит фиксируются при запуске.

## 1. Область и принципы

- Проверяется только публичный контракт из [SPEC.md](SPEC.md): класс `TornadoTeapot`, методы взлёта, перемещения, изменения высоты, облаков, портала, посадки, аплодисментов и `get_state()`.
- Приватные имена, внутренние структуры, тексты исключений, read-only-атрибуты и подклассы `int` не проверяются и не нормируются.
- Каждый тест-метод создаёт новый экземпляр через `self.make()`; подготовка состояния выполняется только публичными командами.
- Тесты не содержат `skip`, `expectedFailure`, `xfail` и условных пропусков. Отсутствие реализации даёт `ModuleNotFoundError` в `setUp`.
- Проверяется импорт `from tornado_teapot import TornadoTeapot` (в `setUp`, не на уровне модуля).
- Доменные исключения `TornadoTeapotError`, `InvalidStateError` и `InsufficientResourcesError` импортируются из модуля `tornado_errors`. Модуль входит в поставку тестовой инфраструктуры и должен существовать до реализации; его отсутствие — дефект комплекта, а не ожидаемое состояние. Отказы состояния проверяются как `InvalidStateError`, нехватка ресурсов — как `InsufficientResourcesError`, ошибки аргументов остаются `ValueError`.

## 2. Стек и совместимость

| Параметр | Значение |
|---|---|
| Язык | Python 3.10 или новее |
| Фреймворк | стандартная библиотека `unittest` |
| Внешние зависимости | не требуются и не устанавливаются |
| Кодировка | UTF-8 |
| Сеть | не требуется; проверка выполняется без сетевых обращений |
| ОС | Windows или Linux |
| Запуск | из корня репозитория |

`pytest` в SPEC.md указан как допустимый, но данный набор использует только `unittest`, чтобы не устанавливать зависимости.

## 3. Состав тестового набора

| Файл | Назначение | Число тест-методов |
|---|---|---|
| `tests/__init__.py` | пакет тестов для discovery | — |
| `tests/helpers.py` | `INITIAL_STATE`, `ContractCase`, проверки состояния и отказов | — |
| `tests/test_acceptance.py` | приёмочные сценарии ПТ-01 — ПТ-22 | 22 |
| `tests/test_boundaries.py` | дополнительные граничные сценарии ДТ-01 — ДТ-11 | 11 |
| `tornado_errors.py` | доменные исключения; не тестовый файл, компилируется вместе с набором | — |
| **Итого** | | **33** |

Число 33 — текущий набор (22 ПТ + 11 ДТ); ДТ-11 добавлен по замечанию C01 ревью Агапова А. М. и входит в каталог, команды и критерии.

Один тест-метод соответствует одному ПТ/ДТ-кейсу. В `test_boundaries.py` варианты одного ДТ выполняются через `subTest`; это не отдельные тест-методы и не отдельные «входы» в отчёте `unittest`. Например, `test_dt04_*` — один метод с несколькими `subTest`, а не множество отдельных тестов.

Ссылки на конкретные методы в [TEST_CASES.md](TEST_CASES.md) даны по префиксу `test_ptXX_*` / `test_dtXX_*`; полные имена приведены в файлах тестов.

## 4. Контракт тестовой инфраструктуры

`tests/helpers.py` задаёт:

```python
INITIAL_STATE = {
    "x": 0,
    "y": 0,
    "altitude": 0,
    "energy": 60,
    "clouds": 0,
    "is_airborne": False,
}
```

`ContractCase(unittest.TestCase)`:

- `setUp()` импортирует `tornado_teapot` и сохраняет `self.teapot_class`. Импорт отсутствующего модуля даёт `ModuleNotFoundError` в `setUp` — тест помечается как `error`, а не `skipped`.
- `make()` создаёт новый экземпляр.
- `command(teapot, method_name, *args, **kwargs)` вызывает метод и проверяет, что результат — `None`.
- `reject(teapot, exc_type, method_name, *args, **kwargs)` ожидает исключение, сохраняет снимок `get_state()` до вызова и после исключения сверяет состояние через `assert_state()` — то есть проверяет и значения, и точные типы всех полей. Возвращает пойманное исключение.
- `assert_state(teapot, expected)` сравнивает полный словарь, набор ключей и точные типы: `int` для `x`, `y`, `altitude`, `energy`, `clouds`; `bool` для `is_airborne`. Используется как для ожидаемых состояний, так и для снимков «до отказа».
- Доменные исключения импортируются из `tornado_errors` и передаются в `reject()` как ожидаемый тип: `InvalidStateError` для недопустимого состояния, `InsufficientResourcesError` для нехватки энергии или облаков, `ValueError` для ошибок аргументов.
- `get_state()` обязан возвращать новый словарь; ПТ-21 и ДТ-10 дополнительно проверяют, что снимки — разные объекты и ранее выданный снимок не изменяется последующими командами.

Тесты не обращаются к приватным полям и не зависят от порядка ключей.

## 5. Команды

Все команды выполняются из корня репозитория. До реализации `tornado_teapot.py` команды компиляции и сбора тестов применимы к тестовому набору, а полный запуск даёт ожидаемые ошибки `setUp` (раздел 6).

### 5.1 Компиляция тестов

```bash
python -m compileall -q tests tornado_errors.py
```

Эквивалентная точечная проверка:

```bash
python -m py_compile tests/__init__.py tests/helpers.py tests/test_acceptance.py tests/test_boundaries.py tornado_errors.py
```

После появления реализации дополнительно:

```bash
python -m py_compile tornado_teapot.py
```

`py_compile` проверяет синтаксис, но не импорты и не поведение.

### 5.2 Сбор тестов без запуска

```bash
python -c "import unittest; suite = unittest.defaultTestLoader.discover('tests', top_level_dir='.'); print(suite.countTestCases())"
```

Ожидаемое значение — `33` (22 ПТ + 11 ДТ). Команда импортирует тестовые модули, но не вызывает `setUp`, поэтому не требует наличия `tornado_teapot.py`; это проверка коллекции, не прогон. Модуль `tornado_errors.py` при этом должен присутствовать: он импортируется тестами для проверки доменных исключений.

### 5.3 Полный запуск

```bash
python -m unittest discover -s tests -t . -v
```

### 5.4 Целевые запуски

По файлам:

```bash
python -m unittest tests.test_acceptance -v
python -m unittest tests.test_boundaries -v
```

По классу:

```bash
python -m unittest tests.test_acceptance.TestAcceptance -v
python -m unittest tests.test_boundaries.TestBoundaries -v
```

Для одного известного метода скопируйте полное имя из файла тестов, например:

```bash
python -m unittest tests.test_acceptance.TestAcceptance.test_pt05_zero_vector -v
```

Для отдельного ДТ используется полное имя соответствующего `test_dtXX_*` из `tests/test_boundaries.py`.

## 6. Ожидаемое поведение до реализации

При отсутствии `tornado_teapot.py`:

| Проверка | Ожидаемый результат |
|---|---|
| Компиляция тестов и `tornado_errors.py` | успешно, синтаксических ошибок нет |
| `countTestCases()` | `33` (22 ПТ + 11 ДТ) |
| Полный запуск | 33 теста, 33 `error`, 0 `failure`, 0 `skipped`; код возврата 1 |
| Причина ошибки | `ModuleNotFoundError: No module named 'tornado_teapot'` в `ContractCase.setUp` каждого метода |
| Статус | красный (до реализации) |

`tornado_errors.py` должен присутствовать до реализации: это часть тестового комплекта, а не реализуемый модуль. Если при отсутствии `tornado_teapot.py` число ошибок не совпадает с числом методов (33), проверяются сбор тестов и целостность `tests/`; отдельное отсутствие `tornado_errors.py` — ошибка импорта тестовых модулей, а не ожидаемое красное состояние.

## 7. Критерии успешного прогона после реализации

Одновременно:

1. `countTestCases()` возвращает `33` (22 ПТ + 11 ДТ).
2. `python -m unittest discover -s tests -t . -v` завершается с кодом 0.
3. В итоговой строке: `Ran 33 tests`; `OK`; отсутствуют `failures`, `errors` и `skipped`.
4. Все `subTest` внутри `test_dtXX_*` проходят; сообщения о вложенных ошибках отсутствуют.
5. Ручные проверки ФТ-16 из раздела 8 выполнены.
6. `README.md` содержит версию Python, команду запуска тестов, описание команд и воспроизводимый пример полёта (SPEC.md, раздел 5).
7. Зафиксированы факт запуска, версия Python, ОС и коммит по форме раздела 9.

Зелёный прогон тестов — необходимое, но не единственное условие приёмки MVP из SPEC.md, раздел 8.2; дополнительно проверяются документация и демонстрация.

## 8. Ручные проверки ФТ-16

Автоматические тесты проверяют детерминизм последовательности, но ФТ-16 дополнительно проверяется вручную:

1. **Зависимость вычисления состояния.** Просмотреть модуль и убедиться, что состояние и результаты команд не зависят от случайных чисел, времени, сетевых обращений и внешних сервисов. Импорт библиотеки сам по себе не является нарушением; важен её вклад в вычисление состояния. Критерий — SPEC.md, ФТ-16.
2. **Повторяемость в разных процессах.** Дважды выполнить одну и ту же последовательность из приложения Б SPEC.md в отдельных процессах Python и сравнить **словари** `get_state()`. Порядок ключей не нормируется; должны совпасть значения и точные типы:
   ```
   {'x': 70, 'y': -40, 'altitude': 0, 'energy': 51, 'clouds': 0, 'is_airborne': False}
   ```
3. **Без сети.** Отключить сеть (или использовать изолированное окружение) и повторить демонстрационный полёт и полный тестовый прогон. Сетевых обращений и внешних сервисов быть не должно.
4. **Детерминизм отказов.** Повторить последовательность с ошибочной командой: снимок до и после отказа должен совпадать при каждом запуске.

Метрики покрытия (проценты строк, ветвей и т. п.) не измеряются; критерий — перечень сценариев и фактический результат.

## 10. Ограничения плана

- Не проверяются GUI, БД, пользователи, сетевые функции и сохранение полёта между запусками — этих требований нет в первой версии. Запрет сетевых обращений при вычислении состояния (ФТ-16) проверяется по разделу 8.
- Не проверяются приватные детали реализации и тексты сообщений.
- Не выполняются нагрузочные, фаззинговые и мутационные испытания: они не входят в MVP.
- При конфликте теста и SPEC.md вопрос решается через [REVIEW.md](REVIEW.md), а не правкой ожиданий.
